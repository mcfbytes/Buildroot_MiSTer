## 1. The direction inverted

Every fork-sync record written before 2026-09-12 describes a commit that landed on the fork
and had to be pulled *in*. Five of these six went the other way:

- `697bfee03`, `b033b3335`, `d3aa7de23`, `6a581bac4` are **our own PRs** (#93, #94, #95, #98),
  opened by `mcfbytes` from `docs/kernel-recon/fork-sync-2026-09/upstream-candidates/` and
  merged 2026-09-12 within three minutes of each other.
- `66ba034e3` is PR #92, somebody else's patch — but it merged carrying *our* review fix
  (§2).

Only `912aa5608` (Sorgelig) is genuinely inbound, and even that one we already had.

`scripts/check-fork-sync.sh` cannot tell inbound from outbound; it only knows the fork moved.
**That is correct and should stay that way.** "We sent it" is a claim like any other, and the
record is what proves it — an outbound commit that quietly diverged on the way through review
is exactly the thing a queue with a direction flag would have waved past. `66ba034e3` is that
case, and it is the reason this paragraph is not hypothetical.

What the reader of a future queue should take from this: a run of rows authored by us is not
backport work, it is *confirmation that the upstreaming landed* — and the disposition to
write is "already ours, here is the line/patch", not a port.

## 2. The merged hunk was not the PR-head hunk

`fork-sync.conf` and `0049`'s own header both carried a four-item WHEN-#92-MERGES checklist.
Item (2) — re-diff the merged form against the PR-head diff — came with a prediction, drawn
from the two precedents in the 2026-09 increment (PR #88 head `97887b3413` → merged
`9854075c8`, PR #91 head `9537eb33c0` → merged `41c45f378`, `git patch-id --stable` identical
across each pair): *"a modified hunk is possible but has not been observed here, so this is a
cheap check, not an expected change."*

It changed.

| | diff | `git patch-id --stable` |
|---|---|---|
| recorded PR head `a14b5e8e1` | 20 / −12 | `6d984de7390ed86b0aebec0d4c791ab59e6a184f` |
| final PR head `fd682da6a5` | 29 / −12 | `5a72829339e3081ca644a831027f734c63fe8d3f` |
| merge `66ba034e3` | 29 / −12 | `5a72829339e3081ca644a831027f734c63fe8d3f` |

The precedent was not wrong — it was about the *maintainer re-committing a PR on landing*, and
it still holds: the final head and the merge are byte-identical. What it did not cover is a PR
**revised while open**.

**Why it was revised: this repo's own review.** Wave 4 of the 2026-09 increment found that PR
#92's reorder dropped vanilla's "first handshake failed → skip the baudrate block" fallback,
turning a probe vanilla completes into one that fails for any USB-bus `057e:2009`/`2017`/`200e`
device that does not answer the first handshake. `0049` was authored *with* the fix (a
`bool usb_handshook` local) and the finding was written up as
`fork-sync-2026-09/upstream-candidates/08-hid-nintendo-pr92-handshake-fallback.NOTE.md`. It was
posted to PR #92 on 2026-09-11; the submitter adopted the exact construct in `fd682da6a5`; the
merged commit message says *"That regression was spotted in review by mcfbytes."*

**The lesson, in one line:** at merge time, diff the merge against the **recorded** head SHA,
not against `refs/pull/N/head` as it stands then — those can be different commits, and the
recorded one is the only one your carried patch was actually written against.

(One correction absorbed from the same PR thread and re-verified against
`git show c129b0fac:drivers/hid/hid-nintendo.c`: on this base the *fatal* step in that block is
the second handshake, not the baudrate command — a `JC_USB_CMD_BAUDRATE_3M` failure is
downgraded to `hid_warn` and execution continues. The conclusion is unchanged.)

## 3. Two patches aligned to what upstream merged

`0049` and `0001` each now produce source **byte-identical** to the fork's, where before they
differed by a comment upstream added:

- `0049` — the merge added a 7-line comment above the `if (usb_handshook && …)` guard.
- `0001` — PR #98 added `/* MiSTer: memremap() returns NULL on failure, never an ERR_PTR */`
  above the `memremap()` call. Adopted in **both** copies (`linux-patches/` and
  `linux-patches-beta/`, whose own header requires them to stay in lockstep).

Same call as the 2026-09 increment's `0001` `fb_sys_read`/`fb_sys_write` alignment (owner
decision D4), for the same reason: it keeps `scripts/export-kernel-tree.sh`'s output and the
tree-diff attribution free of a delta that would otherwise have to be re-explained every
increment. **No code changed** — a comment cannot alter codegen, so the Wave-4 compile of this
exact code still stands.

Verified after the edits (measured, not assumed): the patched `joycon_init()` and
`fb_probe()` resource block on a pristine 6.18.52 tree diff **empty** against
`git show 66ba034e3:drivers/hid/hid-nintendo.c` and
`git show 6a581bac4:drivers/video/fbdev/MiSTer_fb.c`.

Not aligned, deliberately: `0039` keeps its multi-line rationale where upstream took a
one-liner (our header has to carry the forward-port provenance), and `0022` keeps `hid_warn`
where the fork still logs `hid_err` on a path that then sets `ret = 0` and continues — an
error message followed by a successful probe reads as a bug in the log. Both are recorded in
their records so the next tree-diff does not re-discover them as unexplained deltas.

`fork-sync-2026-09/env.md` had to record that kernel.org was unreachable and the gregkh mirror
lagged a release, so every vanilla quote behind the previous ten dispositions is against the
6.18.49 release commit rather than the pinned tag. **cdn.kernel.org answered on 2026-09-14.**

Both tarballs were downloaded and checked against this repo's own recorded signed-manifest
hashes *before use* — `board/mister/de10nano/patches/linux/linux.hash`
(`2b69564f…` for 6.18.52) and `package/linux-rt/linux-rt.hash` (`039aef84…` for 7.2.6) — so the
trees behind every quote in this increment are the ones the build actually uses.

All three series replay at `patch -p1 -F0` against pristine pinned trees:

`scripts/lint-kernel-patches.sh`: PASS, 47 patches across 4 series `git am`-able.

The de10nano series is 39 rather than the 38 it was when this increment started:
`0051-perf-revert-no-slang-al-addr-stub-mismatch.patch` landed on master the same day
(`91e3fe6`), reverting a half-backported stable commit that broke `NO_SLANG=1` perf builds on

**Half the caveat, not all of it.** This closes the *loud* half by measurement rather than by
waiting for CI: no carried hunk has rotted against the real pins. The *silent* half is open —
the `.49 → .52` stable-drift walk has not been re-run, so a stable commit that changes the
*context* a carried hunk reasons about (rather than moving it) would still go unnoticed.
`env.md`'s one-command re-check is now runnable; that is the next increment's cheapest win.

## 5. One finding that is not about the queue

`b033b3335`'s Kconfig quote explains something ADR 0031
(`docs/decisions/0031-secure-by-default-network-posture.md`) recorded only as an observation —
that the RT kernel has no iptables filter table:

```
config NETFILTER_XTABLES_LEGACY
	bool "Netfilter legacy tables support"
	depends on !PREEMPT_RT
```

`board/mister/de10nano/linux-rt.fragment` sets `CONFIG_PREEMPT_RT=y`, so when Buildroot layers
it over `linux.config` and runs `olddefconfig`, `NETFILTER_XTABLES_LEGACY` is forced off and
takes `IP_NF_IPTABLES_LEGACY`, `IP_NF_FILTER` and `IP_NF_TARGET_REJECT` with it — silently,
the way an unmet `depends on` always does. This is **not** a config oversight and cannot be
fixed by adding symbols to the RT fragment: the dependency is upstream's and deliberate. A
firewall on the RT kernel has to go through nftables, which is a userspace-package question.
Flagged, not acted on — ADR 0031 is still PROPOSED (PR #168) and this increment does not
pre-empt it.
