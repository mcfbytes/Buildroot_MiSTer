## 1. `7a65ca02c` — the SD read timeout MiSTer lost in the 5.15 → 6.18 move

**Carried as `board/mister/de10nano/linux-patches/0052-mmc-dw-mmc-socfpga-max-data-timeout.patch`.**

Mainline `6a8c2018e872` ("mmc: dw_mmc: Allow lower TMOUT value than maximum", v5.17) stopped
programming the maximum data timeout for every transfer and started deriving `TMOUT[31:8]`
from `data->timeout_ns`. `mmc_set_data_timeout()` asks for 100 ms on an SD read, so on the
DE10-Nano's 50 MHz controller clock `TMOUT` reads back `0x4C4B40FF`. The software read timer
is armed from that same register —

```
linux-6.18.52 drivers/mmc/host/dw_mmc.c:2003-2025
        drto_clks = mci_readl(host, TMOUT) >> 8;
        ...
        drto_ms += 10;   /* add a bit spare time */
```

— and with IDMAC there is no intermediate progress interrupt, so that ~110 ms has to cover a
whole multi-block request, up to 1 MB. 5.15 allowed ~346 ms.

**Why it is worth carrying even unproven.** When a request misses the budget,
`mmc_blk_mq_rw_recovery()` retries, then hardware-resets the card and re-reads the request one
sector at a time. No `-110` is printed, dw_mmc does not touch its debugfs `err_stats` on that
path, and the only dmesg trace is a repeated `Bus speed (slot 0) = 50000000Hz ...` from card
re-init. A user sees stutter and long loads; nothing sees an error.

**What it is not.** Not a backport and not a revert. `6a8c2018e872` was a deliberate change
nobody upstream has repaired, so there is no fix to pull in. What the same generation of work
added is a per-platform escape hatch — `drv_data->set_data_timeout`, consulted first thing in
`dw_mci_set_data_timeout()` (6.18.52 `dw_mmc.c:1285-1293`) — whose only in-tree user in either
of our kernels is Exynos (`dw_mmc-exynos.c:577`, `:649`). The carry adds a socfpga user of an
upstream hook; no core code changes.

Measured absent from **both** pins, not inferred from one: `grep -n set_data_timeout
drivers/mmc/host/dw_mmc-pltfm.c` returns nothing (exit 1) in `linux-6.18.52` *and* in
`linux-7.2.6`, and `socfpga_drv_data` carries `.init` alone in both
(`dw_mmc-pltfm.c:99-101` / `:89-91`). That distinction is 6332499e7's lesson: the question is
never "is it in mainline", it is "is it in the kernel we build".

**Beta gets a symlink, DE25 does not get it at all.** The added lines are byte-identical on
6.18 and 7.2 — 7.x rewrote `dw_mci_socfpga_priv_init()`'s clock-phase parsing *above* the
anchor and left `socfpga_drv_data` alone — so `linux-patches-beta/` links to the shared file
(hunk at offset −10 on 7.2.6, zero fuzz). The DE25 is excluded and this is the first mmc patch
where the two boards genuinely diverge: `socfpga_drv_data` is reached only through
`{ .compatible = "altr,socfpga-dw-mshc", .data = &socfpga_drv_data, }`, the Agilex 5 SD
controller is a Cadence SDHCI part (`0101`), and `board/mister/de25nano/linux.config` has **no
`CONFIG_MMC_DW` at all** — `dw_mmc-pltfm.c` is not even compiled there. Contrast `0020`, which
*is* on all three series because it changes the mmc **core**.

**What is not proven, kept rather than rounded off.** The failure mode is demonstrated with an
artificially shortened 30 ms budget, not with a card that fails at the stock 100 ms; the author
estimates a card would need to be slower than ~9 MB/s on 1 MB requests, or show ~100 ms internal
latency spikes. The fork's issue #103 (PSX CHD stutter, slow N64 loads) is a *suspected*
instance, unconfirmed on the reporter's card. The cost of carrying is bounded and stated: an
unresponsive card now takes ~346 ms instead of ~110 ms to fail a read; writes are unaffected
because their 3 s limit already clamped to the maximum.

## 2. `ae4cafc03` — 128 KiB of read-ahead for a count that stops on the first page

**Carried as `0053-exfat-dir-count-readahead-one-page.patch`, 6.18-only.**

`exfat_count_dir_entries()` walks a directory only to count sub-directories and returns at the
first `TYPE_UNUSED` entry — usually inside the first page. Every page-aligned entry on that walk
goes through `exfat_get_dentry()`, which triggers the read-ahead sized for a real directory
read:

```
linux-6.18.52 fs/exfat/dir.c:658-666
        #define EXFAT_MAX_RA_SIZE     (128*1024)
        static int exfat_dir_readahead(struct super_block *sb, sector_t sec)
        ...
                unsigned int max_ra_count = EXFAT_MAX_RA_SIZE >> sb->s_blocksize_bits;
```

The MiSTer workload counts thousands of directories in a row, so the amplification *is* the
cost. PR #106's numbers on a frozen 1,896-file / 4.86 GB Arcade workload: the Update All
installed-files pass at **77.677 s / 181.2 MB of SD reads** on stock 6.18 against **26.817 s /
39.5 MB** patched — and 5.15 was 39.006 s / 41.5 MB, so the patched 6.18 is faster than the
kernel it replaced rather than merely level with it. Those are the submitter's measurements on
his hardware; nothing here has an SD card or an exFAT volume, so this increment cites them, it
does not reproduce them.

**It composes with `0050`, measured.** `0050` (fork Q6, Giancarlo Erra) plugs the same
function's `sb_breadahead()` loop; this changes the signature, the `max_ra_count` initialiser
and the callers. No hunk overlaps. Applying `0050` then `0053` to a pristine 6.18.52
`fs/exfat/dir.c` yields a region from `#define EXFAT_MAX_RA_SIZE` to
`enum exfat_validate_dentry_mode` that diffs **empty** against
`git show ae4cafc03:fs/exfat/dir.c`, and so does `exfat_count_dir_entries()`. The fork commit's
own message ("existing block plugging … preserved") confirms it was written on top of the plug.

### 2.1 A fourth kind of 7.x exclusion — and the first that is not safe to force

The 7.x exclusion list now has four entries and four *different* reasons:

| Patch | Why 7.x does not get it |
|---|---|
| `0047` | 7.x already has the **same mainline commit** |
| `0050` | 7.x has mainline's **own, different** solution |
| `0051` | 7.x was **never broken** — the defect is 6.18.y's incomplete backport |
| `0053` | 7.x lacks the **function to bound** — but is **not fixed** |

That last row is the one to read twice. `0050`'s exclusion reads "7.x already solved it", and
`0053` sits in the same function, so the lazy inference is that 7.x is fine here too. It is
not. 7.2.6's `exfat_get_dentry()` still reads ahead `ra_count = sect_per_clus`, capped by
`EXFAT_BLK_RA_SIZE(sb) = min(bdi->ra_pages, bdi->io_pages)` — 128 KiB at the default
`read_ahead_kb` (`exfat_fs.h:84-86`, `fatent.c:159-185`, `dir.c:645-658`) — and
`exfat_count_dir_entries()` (`dir.c:1175-1215`) goes through it unchanged. **The same read
amplification is present on the 7.2.x beta kernel and on the DE25, in a different shape.**

And the exclusion does not fail cleanly. At `-F0` against pristine 7.2.6:

```
Hunk #1 FAILED at 656.
Hunk #2 FAILED at 690.
Hunk #3 FAILED at 707.
Hunk #4 succeeded at 664 (offset -52 lines).
Hunk #5 succeeded at 1196 (offset -67 lines).
3 out of 5 hunks FAILED
```

Two hunks *succeed* — the new public `exfat_get_dentry()` wrapper, whose context survived the
7.x refactor, and the `exfat_count_dir_entries()` call site. A forced apply would leave
`exfat_get_dentry()` recursing into itself and calling an `exfat_get_dentry_ra()` that does not
exist. `patch -F0` exits 1 and Buildroot stops the build first, which is the only reason the
exclusion is safe. Recorded in the patch header, in `linux-patches-beta/series` and in the DE25
README, because "just force it" is the natural next move for someone who reads only the first
three rows of that table.

## 3. `0b2ffdd1d` — independent convergence, and the defect it exposed in ours

**Already carried in `0037`. Which is exactly where the work was.**

### 3.1 Nobody sent anything

`0037`'s header has said since the 2026-07-15 forward-port that `BTN_Z` is declared

> per-device via `input_set_capability()` instead of editing the `ps_gamepad_buttons[]` table,
> which 6.18 shares with DualShock 4 (the fork's 5.15 table was DualSense-only).

The fork's own 6.18 port edited that table anyway, shipped it, and hit precisely the
renumbering that sentence predicts. `BTN_Z` is `0x135`, between `BTN_WEST` (`0x134`) and
`BTN_TL` (`0x136`), so advertising it on a DualShock 4 shifts every higher button up one index
in the `EV_KEY` bitmap Main_MiSTer walks —

```
Main_MiSTer gamecontroller_db.cpp:198, 207-217
        if (ioctl(dev_fd, EVIOCGBIT(EV_KEY, sizeof(keybits)), keybits) >= 0)
                for (int i = BTN_JOYSTICK; i < KEY_MAX; i++)
                        if (test_bit(i, keybits)) { btn_map[btn_cnt] = i; btn_cnt++; }
```

— so the DS4 `gamecontrollerdb` rows resolved one button low and Options read as Guide (their
issue #101). PR #107 fixes it by arriving at this repo's conclusion, two months later, from the
opposite direction.

**This is a third thing the queue can be.** 2026-09-14 recorded that the direction had
*inverted* — five of six rows were our own merged PRs. This one is neither inbound nor
outbound: it is independent agreement, and its value is somebody else's hardware ("DS4 Options
acts as Start, and the PS button correctly opens the OSD") confirming a decision this repo made
on reading alone in July.

### 3.2 No `bN` index moves — measured, so no owner decision is needed

Adopting the merged shape changes *which line of C* declares `BTN_Z`, not *which devices have
it*. Before and after, on this image: DualShock 4 gets vanilla's 13 codes and no `BTN_Z`;
DualSense and DualSense Edge get those 13 plus `BTN_Z`. With the full series applied to
pristine 6.18.52 and 7.2.6, `ps_gamepad_buttons[]` and `ps_gamepad_create()` both diff **empty**
against `git show 0b2ffdd1d:drivers/hid/hid-playstation.c`.

For the record, the DualSense layout this preserves — where the shipped `platform:MiSTer` PS5
rows' `guide:b11`, `leftshoulder:b5`, `back:b9`, `start:b10` come from:

| bN | code | | bN | code |
|---|---|---|---|---|
| b0 | `BTN_SOUTH` 0x130 | | b7 | `BTN_TL2` 0x138 |
| b1 | `BTN_EAST` 0x131 | | b8 | `BTN_TR2` 0x139 |
| b2 | `BTN_NORTH` 0x133 | | b9 | `BTN_SELECT` 0x13a |
| b3 | `BTN_WEST` 0x134 | | b10 | `BTN_START` 0x13b |
| **b4** | **`BTN_Z` 0x135** | | b11 | `BTN_MODE` 0x13c |
| b5 | `BTN_TL` 0x136 | | b12 | `BTN_THUMBL` 0x13d |
| b6 | `BTN_TR` 0x137 | | b13 | `BTN_THUMBR` 0x13e |

DS4 is the same list minus `BTN_Z`, every index from b4 on one lower.

### 3.3 "Already carried" is not "nothing to do"

Comparing the merged shape against ours turned up a defect in **ours**.

`0b2ffdd1d` declares the capability *inside* `ps_gamepad_create()`, via a `bool
has_mute_button` parameter — that is, **before** that function's own `input_register_device()`
(6.18.52 `drivers/hid/hid-playstation.c:783`). `0037` declared it on `ds->gamepad` *after*
`ps_gamepad_create()` returned.

- **evdev cannot tell.** `EVIOCGBIT` reads `dev->keybit` live, so Main_MiSTer was unaffected and
  `0037`'s hardware verification still stands.
- **joydev can.** `joydev_connect()` copies `dev->keybit` into its `keymap`/`keypam` once, when
  the handler attaches — and `input_attach_handler()` runs *inside* `input_register_device()`.
  So `/dev/input/jsN` on a DualSense reported **13 buttons and no `BTN_Z`** where stock 5.15
  reported 14. `CONFIG_INPUT_JOYDEV=y` (`board/mister/de10nano/linux.config:344`), so that
  interface ships.

`0037` was therefore realigned to the merged shape in **both** copies. Same alignment call as
`0049`/`0001` on 2026-09-14 and for the same second reason — it keeps the export's tree-diff
free of a delta that would otherwise be re-explained every increment — but **unlike those two
this one is a code change, not a comment**, and is priced as such here rather than buried.

Secondary, and not a reason on its own: the initial `add` uevent's `KEY=` variable is also a
snapshot taken during `device_add()`, so it lacked `BTN_Z`. udev's `input_id` builtin reads
`capabilities/key` from sysfs live, so `ID_INPUT_*` was never affected. Noted so the next reader
does not re-derive it as a separate finding.

### 3.4 Not the "userspace should accept mainline names" class

The maintainer's stated preference — upstream PRs #96/#97 closed in favour of Main_MiSTer
#1307/#1308 — applies to kernel-side *restorations* of stock strings that userspace could
accept instead. This is the opposite: it **removes** a capability the fork's own port added on
top of mainline, restoring vanilla's DS4 bitmap. No userspace change could have fixed it; the
`bN` ordinal is derived from the kernel's bitmap by construction.

### 3.5 It supersedes nothing

`0032` is hid-nintendo, a different file. `0033` (DualSense player-id LED) and `0042` (stock
lightbar LED names) touch `dualsense_create()` and the LED block, not `ps_gamepad_create()` or
the button table. `0037` remains the only source of `BTN_Z`, of the `BTN_Z` report in
`dualsense_parse_report()`, and of the userspace-owned `:mute` LED class device — none of which
`0b2ffdd1d` touches. The full-series replays in §4 are the proof that all four coexist.

### 4.3 A pre-existing blocker found on the way: the export cannot run on master

`scripts/export-kernel-tree.sh` **replays this increment's series perfectly** — "Applied 41/41
carried patches cleanly", "Applied 1/1 upstream-only patches cleanly" — and then dies:

```
export-kernel-tree: detected zero kernel-module packages in the
DE10 defconfig (configs/mister_de10nano_defconfig):
  …/configs/mister_de10nano_defconfig
That is almost certainly a parsing bug in this script rather than the truth — the image
ships xone and the Realtek WiFi drivers. Refusing to export a tree missing them.
```

**This is not caused by anything here.** Reproduced on an unmodified `git archive HEAD` of the
base commit (`912a293`), with no patch from this increment present.

The cause is one refactor further than the script's own warning anticipated. Its section-6b
comment (`scripts/export-kernel-tree.sh:177-190`) explains that reading a *single* fragment
became wrong when the 2026-09 fragment split moved `BR2_PACKAGE_XONE` and
`BR2_PACKAGE_RTL8852CU_MORROWNR` into `de10nano-image.fragment`. The ADR 0030 profile work then
replaced those literal selections with a **profile package**:
`configs/mister_de10nano_defconfig:69` is now `BR2_PACKAGE_MISTER_DRIVERS=y`, and the four
module packages are reached through Kconfig `select` statements in
`package/mister-drivers/Config.in`. Section 6b greps for literal `BR2_PACKAGE_*=y` lines that
resolve to a `package/<dir>/<dir>.mk`, so it now finds `mister-drivers` — which is not itself a
kernel-module package — and nothing else. It fails closed, which is the right behaviour, but it
means **no export can be published from master today**.

Deliberately **not fixed here**. The fix is a design question (resolve the profile's `select`
lines? drive a real kconfig resolution? something else), it belongs to the ADR 0030 workstream
that introduced the profile packages, and quietly editing that script inside a fork-sync PR
would be exactly the scope creep this directory's write-ups argue against. It needs its own
issue.

To get `check-export-tree.sh` a tree to check, the export above was run from a **scratch copy**
of this branch with the four selected package symbols appended to the defconfig — a throwaway
verification aid, not a committed change. With that one line group present the export completes:
`RESULT: PASS — exported Linux 6.18.52 + 41 carried patches + 1 upstream-only`, 49 commits, tag
`mister-6.18.52`.

**Still open, third increment running:** the *silent* half of the 2026-09 grounding caveat —
the `.49 → .52` stable-drift walk has not been re-run, so a stable commit that changes the
*context* a carried hunk reasons about (rather than moving it) would still go unnoticed.

## 5. Open items this increment created

1. **7.x exFAT directory-count amplification is real and uncarried** (§2.1). A 7.x fix would be
   original code with no fork commit to trace to, which is both an authorship question and a
   `reduce.py` orphan-invariant question. Two honest routes: write it and send it to the fork
   first, so the carry has a provenance; or add it under `NO_FORK_ORIGIN` the way `0051` is, with
   the reason in-band. Not decided here — it affects the RT beta kernel and the DE25, neither of
   which is the shipping image.
2. **`0052` has not been exercised on this project's rig.** Boot-tested by its author on a
   DE10-Nano; the failure it prevents has never been reproduced at stock settings by anyone.
3. **`scripts/export-kernel-tree.sh` is broken on master** (§4.3) — pre-existing, needs its own
   issue against the ADR 0030 profile-package workstream. Until it is fixed the export, and
   therefore any upstream publication, cannot run.
4. **`0037`'s realignment has not been re-run on hardware.** The `EV_KEY` bitmap is provably
   unchanged, so the DualSense/DS4 mapping cannot have moved, but the joydev button count that
   motivated the change (13 → 14 on a DualSense) is an inference from `joydev_connect()`'s source,
   not a measurement — `cat /proc/bus/input/devices` and `jstest` on a real DualSense would close
   it in a minute.
